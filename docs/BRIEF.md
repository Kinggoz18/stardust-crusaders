# Brief: Stardust Crusaders platform (backend + admin dashboard)

Owner: Chigozie Muonagolu. Business: **Stardust Crusaders**, a small studio shipping three mobile games: **One Spark** (fireworks puzzle, built), **Loom Rush** (planned), **Borrowed Time** (planned; future async multiplayer). All three are TypeScript + Vite + PixiJS + Capacitor, Android first.

## What to build (this task = a solid, verified foundation, not every feature)
A monorepo (Bun workspaces) with:

1. `apps/api`: **Bun + Fastify (TypeScript)** HTTP API that runs on a **real VPS** (long-running Node-style server, Docker + docker-compose with Postgres and a reverse proxy such as Caddy, health/readiness endpoints, structured logs, graceful shutdown, env-validated config; deploy files only, never deploy).
2. `apps/admin`: the **admin dashboard for Stardust Crusaders staff**, deployed on **Cloudflare Pages: edge runtime only** (no Node APIs). Use a static SPA (Vite + React + router) plus Pages Functions as a thin edge proxy to the API so the browser never holds the API service credentials. Admin pages are real sub-routes (no one giant page).
3. `packages/schema`: shared zod schemas + TS types used by both apps and (later) the games: accounts, per-game progress documents, telemetry events, ad/IAP provider payloads, error shapes.
4. `docs/`: ARCHITECTURE.md, ROADMAP.md (see "Later, design only"), SECURITY.md, RUNBOOK.md (deploy, backup/restore, rotate keys), API.md (generated from the zod/Fastify schemas if possible).

### Backend capabilities to implement now
- **Accounts:** anonymous device accounts first (create on first launch, returns account id + short-lived access token + refresh token), later linkable to Apple/Google/email (design the table now, implement linking as a stub with tests of the contract). One account can hold progress for several games. Account deletion and data export endpoints (NDPA 2023 + GDPR: consent flags, no pre-ticked boxes, accept/reject equal weight in any UI).
- **Games registry + per-game progress:** `games` table (one-spark, loom-rush, borrowed-time). Progress is stored as a **versioned JSON document per account per game**, validated by that game's zod schema in `packages/schema`, with server-side sanity checks (for One Spark: stars only go up, coins never negative, firstClear flags monotonic, etc.). Conflict handling: server revision numbers + last-writer-wins with a reject on stale revisions and a documented merge for One Spark (stars OR-merge like `mergeStars`, coins by the server's own ledger; see `games/one-spark/save.ts`, `wallet.ts`, `economy.json`, `resume.ts`). One Spark's real save shape is the reference for its schema; Loom Rush and Borrowed Time get **draft schemas derived from their FINAL_PLAN docs** (Borrowed Time: `IslandSnapshot`, append-only event log, command log, per FINAL_PLAN section 12), clearly marked draft.
- **Coin/wallet ledger** (append-only) so economy rules can later be enforced server-side; One Spark's economy numbers live in its repo's `economy.json` (copy of current values is in `games/one-spark/`).
- **Telemetry:** batch event ingestion (`POST /v1/events`) with consent flag, per-event schema validation, dedupe by event id, payload size limits, rate limiting; tables built for per-game funnels (tier/level reached, session length, quit point). Telemetry is anonymous unless the player is signed in; store the minimum.
- **Ads provider abstraction:** one interface (`AdProvider`) with a `none` implementation and one provider-agnostic server-side verification endpoint for **rewarded-ad reward callbacks** (idempotent by transaction id, signature check pluggable). The ad network is not chosen yet (candidates: AdMob, AppLovin MAX); do not hard-code one. One Spark currently has a client stub that always pays (`games/one-spark/ads.ts`); the server verification replaces that.
- **IAP/subscription webhooks:** a RevenueCat webhook endpoint stub with signature verification, idempotency by event id, and tests that replay the same webhook twice (payments rules in `skills/payments-testing`). Test keys only; never live.
- **Admin API (`/admin/v1/*`):** separate auth from players. Staff accounts with Bun.password (argon2id), mandatory TOTP 2FA, short sessions, roles (`owner`, `support`, `viewer`), audit log of every admin read of personal data and every write. Endpoints: list/search accounts (by id, device id, email once linked), account detail with per-game progress (formatted per game schema), wallet ledger, recent events timeline, ban/unban + reset-progress (owner only, audited, reversible via backup row), and basic metrics (new accounts, DAU/WAU, per game: levels cleared distribution, retention D1/D7 from events).
- **Rate limiting, CORS allowlist, security headers, request size limits, consistent error shape, idempotency keys on mutating endpoints.**
- **Database:** Postgres with **Drizzle ORM** (or Kysely if you can justify it in ARCHITECTURE.md) and SQL migrations that are **expand-then-contract**, each with a tested down migration. Seed script for local dev with fake accounts for all three games (clearly fake, marked).

### Admin dashboard (apps/admin) requirements
Follow `personas/FACET.md` and `rules/ui-copy.mdc`, `rules/ux-structure.mdc` strictly: short audience-appropriate copy (the audience is Stardust staff, not developers: never expose API paths, IDs or status codes in copy), one main task per screen, sub-routes with deep links (`/accounts`, `/accounts/:id`, `/accounts/:id/games/:game`, `/games`, `/metrics`, `/audit`, `/settings/staff`), designed states for loading (skeletons), empty, error, partial, offline, no-permission, success; WCAG 2.2 AA; design tokens (one spacing scale, one type scale, colour tokens, light and dark); looks like a finished product, not an MVP. Landing/login screen included. Responsive down to 360 px. Tables must be keyboard accessible with sortable headers and cursor pagination.
Edge constraints: build must pass `wrangler pages` local dev/build; no `fs`, no Node-only deps; Pages Functions use `fetch` to call the API with a server-side secret; session cookie is httpOnly, secure, SameSite=Strict; CSRF protection on mutating calls.

### Later, design only (write into docs/ROADMAP.md, do NOT build)
Borrowed Time async multiplayer (server tick, authoritative replay of the client command log with seeded RNG, alliances, trading, raiding other players; see `games/BORROWED_TIME_FINAL_PLAN.md` section 12), cloud save linking UX, push notifications, A/B config service, a shared config/remote-flags service, the ad network choice and mediation, and moving from a single VPS to more. Reserve clean module boundaries (`apps/api/src/modules/<name>`) so these slot in later.

## How to work (non-negotiable)
- Read `personas/ANVIL.md` (build + verification), `personas/FACET.md` (UI/UX), `personas/WARDEN.md` (security) and treat them as your standards. Run the loop from ANVIL: plan, name the data shape first, implement in small ordered chunks, test, review, plain commit. Follow `skills/start-of-work`, `skills/agent-guardian`, `rules/*.mdc`. Draft the repo's `AGENTS.md` from `templates/AGENTS.md.template` (names only, no secret values) and a `.cursor/skills/verify-stardust/` verification skill (launch, doctor, drive, evidence, cleanup). Copy the rules from `rules/` into `.cursor/rules/` in the new repo and `templates/commit-hygiene.yml` into `.github/workflows/`.
- **Tests first for each chunk.** API: unit + integration against a **real ephemeral Postgres** (service container in CI, docker-compose locally), no mocked DB. Contract tests for every endpoint from the zod schemas. Webhook idempotency tests (replay twice). Auth tests (expired, tampered, wrong role, wrong account). Admin: Playwright e2e with real clicks, screenshots of every changed route at 360, 768 and 1280 px in every state, axe with zero WCAG 2.2 AA violations (including dialogs), a keyboard walk, copy lint (`templates/check-ui-copy.sh`) exiting 0. One CI script (`bun run ci`) runs lint, typecheck, tests, build for both apps, and the migrations up/down check.
- **Security (Warden):** OWASP Top 10:2025 mindset; a finding counts only with a failing test. Never trust client-computed results. Parameterised queries only, strict payload validation, secrets only via env (provide `.env.example` with names only), no secrets in logs, least-privilege DB role, dependency audit in CI, SECURITY.md with the threat model (accounts, admin, webhooks, telemetry).
- **Commits:** plain Conventional Commits, no signing, no `Signed-off-by`, no `Co-authored-by`, no agent/tool names in any message, never `--no-verify`. **Commit right after every feature or fix whose tests pass; never batch commits** (a restart must not lose progress).
- **Hard rules:** never wipe/reformat disks; do not deploy; do not use live keys; do not push to any other repo. You may use only your own tools: **do not start subagents or hand work to any other model.**
- Keep the VM light: one heavy process at a time; clean up temp files, screenshots, containers and logs you no longer need; keep only evidence the owner must review under `.artifacts/<run-id>/` with a README.
- Be honest: end with a report of what is verified, what is stubbed, and what is unproven. Challenge weak decisions instead of silently going along (put your reasoning in ARCHITECTURE.md decision records).
